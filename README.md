# 暖芽辅导班

面向小型课后辅导班的**微信小程序 + H5 双端**应用。家长进来输一串绑定码就能看到孩子在班里的一天，老师和负责人在同一个应用里跑完作业、积分、兑换、接娃提醒的全部日常。

两端共享同一套领域逻辑（绑定码校验、积分账本、状态机、权限矩阵），后端是零依赖的 Node + SQLite 服务。

---

## 一分钟跑起来

```bash
npm install
npm run dev
```

然后打开 **http://localhost:5173**。

首次启动会自动灌入演示数据，控制台会打印：

```
负责人账号  owner / warm2026
老师账号    teacher / warm2026
学生绑定码：
  张小满   4R90-KWSX
  陈知夏   1WAR-4WA9
  ...
```

**体验路径**：登录页选「老师 / 负责人」用 `owner / warm2026` 进管理端 → 学员页「新增学员」→ 弹窗给出一串绑定码 → 换一个无痕窗口打开同一地址 → 家长入口输入这串码 → 立刻绑定，看到孩子的今日、作业、积分。

> 要求 Node ≥ 22.5（用到内置的 `node:sqlite`，不需要任何原生编译依赖）。

## 绑定码：这个项目的核心

需求是「管理员建一个孩子 → 得到一个唯一固定的绑定码 → 家长登录时输这串码完成绑定」。原始规格里只有一行 `家长提交学生邀请码/匹配信息` 的模糊表述，没有任何字段和规则，所以这部分是补齐的设计：

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 谁生成 | **服务端**在「新增学员」时生成，客户端传 `bindingCode` 会被忽略 | 客户端传入的一切都不可信（design §7） |
| 唯一性 | `students.binding_code` 建唯一索引，生成冲突就换一个重试 | 唯一性靠数据库兜底，不靠随机数运气 |
| 固定性 | 建档后永不自动变化；负责人可在外泄时显式重置（写审计） | 需求明确要求「唯一固定」 |
| 可重复使用 | 同一个码爸爸妈妈都能用 | 不是一次性验证码，是"这个孩子的身份牌" |
| 格式 | 8 位 Crockford Base32：7 位随机 + 1 位校验位，展示成 `K3M9-QX2T` | 去掉 I / L / O / U，家长照纸条手输不会认错 |
| 输入容错 | 自动大写、自动补短横、`O→0`、`I/L→1`、全角转半角 | 中文输入法下全角是高频错误 |
| 本地预校验 | 满 8 位先在本地验校验位，错了当场提示 | 不浪费一次网络请求 |
| 绑定前确认 | 校验位通过后拉一次脱敏姓名预览（`预***`） | 让家长确认"绑的是自家娃" |
| 防穷举 | 同一身份 10 分钟内最多 10 次失败 | 否则能靠爆破枚举出别人家孩子 |
| 审核开关 | 系统设置里可切换「输码即绑定 / 提交申请等审核」，默认前者 | 小班直接绑更顺，大班可以卡一道 |

校验位算法有个坑值得记一笔：字符集大小是 32（2 的幂），**加权求和的权重必须全取奇数**。用偶数权重时单字符错输的拦截率只有 95.2%（`shared/test/binding-code.test.js` 里留了这条回归测试），改成 `2i+1` 后是 100%。

## 项目结构

```
warm-study/
├── shared/          两端共享的领域逻辑（纯 TS，不依赖任何平台 API）
│   ├── src/
│   │   ├── binding-code.ts   绑定码生成 / 归一化 / 校验位
│   │   ├── points.ts         积分账本口径、排行榜排序规则
│   │   ├── state-machines.ts 到班 / 作业 / 错题 / 商品 的状态转移表
│   │   ├── permissions.ts    权限码与角色默认权限
│   │   ├── api-contract.ts   接口契约（三边共用，改这里三边一起报错）
│   │   └── errors.ts         稳定错误码 + 中文提示
│   └── test/        44 个单元测试
├── server/          Node + SQLite 后端（除 shared 外零依赖）
│   ├── src/
│   │   ├── db.ts             建表、索引、事务包装
│   │   ├── core.ts           权限校验、审计、积分账本入口
│   │   ├── services/         身份 / 学员 / 作业 / 到班 / 积分 / 商店 / 错题 / 管理
│   │   └── app.ts            路由表
│   └── test/        104 个接口集成测试
├── h5/              Vite + TS 的 H5 端（小程序风格：自定义 TabBar + 页面栈）
├── miniprogram/     原生微信小程序（24 个页面）
├── design-system/   自动生成的组件库（给设计师看的，含 index.html 单页总览）
├── scripts/         dev / e2e / sync-shared / build-design-system
├── docs/            截图与补充文档
└── specs/           原始规格文档（保留）
```

### 为什么是这个结构

`shared/` 不是"工具函数集合"，而是**业务规则的唯一定义处**。「花积分不降低当期排名」这条规则写在 `points.ts` 的 `countsTowardPeriodScore` 里，服务端算排行榜用它，两个前端展示时也用同一份。想改规则只有一个地方能改。

`miniprogram/shared/` 是 `npm run sync:shared` 从 `shared/dist` 复制过去的（微信小程序不能引用 `miniprogramRoot` 之外的文件）。那个目录**不要手改**。

## 核心业务规则

这些规则在服务端强制执行，前端只是不渲染对应按钮而已：

- **积分余额是流水汇总的结果**。全仓只有 `core.ts` 的 `applyLedger` 一处会写 `students.point_balance`，任何地方都不能直接改余额；`/points/reconcile` 提供只读对账，发现差异只告警不覆盖。
- **余额不允许为负**，扣分前先检查，不够就整个事务回滚。
- **流水永不删除**，撤销靠写一条反向流水实现，原流水标记 `reversed` 后永久保留。
- **花积分不降低当期排名**：周期得分只统计正向且未被冲正的流水，兑换扣除和撤销返还都不计入。
- **兑换是一个事务**：查余额 → 查库存 → 查限兑 → 扣分 → 减库存 → 写记录，任一步失败全部回滚，绝不留下"扣了分没拿到东西"。
- **商品快照**：兑换记录里存的是当时的商品名和价格，后续改价不影响历史。
- **审计只增不删**：敏感操作全部留痕，路由表里根本不存在删除审计的入口。
- **最后一名负责人不可停用或降权**。
- **老师被停用后立刻失去写能力**：停用时同步删掉该账号的全部会话。
- **通知失败不伪装成成功**：没有已绑家长时接娃提醒返回 `delivered: false`，管理端明确提示改用电话。

## 小程序端

```bash
npm run build:shared && npm run sync:shared
```

然后用**微信开发者工具**打开 `miniprogram/` 目录。上线前必做的几件事详见 `miniprogram/README.md`：

1. 把 `miniprogram/utils/api.ts` 里的 `API_BASE` 改成你的后端域名
2. `project.config.json` 里的 `appid` 换成你自己的
3. 小程序后台配置 request 合法域名
4. 订阅消息模板需要自己申请后接入

> **诚实说明**：小程序端的代码逻辑、接口契约和引用路径都做了静态校验（24 个页面三件套齐备、51 个接口调用点全部命中契约、`tsc --noEmit` 通过），但**没有在微信开发者工具里真实渲染或点击过** —— 云端沙箱跑不了开发者工具。最可能需要现场微调的是自定义 TabBar 的挂载和 WXSS 内联 SVG 图标的渲染。H5 端则是在真浏览器里完整跑通并截图验证过的。

## 设计系统

```bash
npm run build:design
```

从 `h5/src/styles.css` 生成 `design-system/`：16 张组件卡片 + 一页总览 `index.html` + `tokens.json`。

每个预览文件都**内联真实的 styles.css 原文**，不是另写的演示样式 —— 所以预览里看到的就是线上的样子，设计师改动能一对一映射回类名。哪天有人改了样式忘了同步设计稿，重跑一次立刻能看出差异。

产物首行带 `<!-- @dsCard group="…" -->` 标记，符合 Claude Design 设计系统项目的导入格式。改版约束（不能引 Web 字体、图标禁用 emoji、家长端排行必须脱敏等）写在 `design-system/README.md` 里。

## 已知边界

- 微信订阅消息未接入（需要真实 AppID 和模板 ID）。
- 图片用 dataURL 存库，适合演示和小班规模；量大了应换成对象存储只存 fileId。
- 后端是单进程 SQLite，适合一个辅导班的并发量。

## 规格文档

`specs/tutoring-miniapp-v1/` 下保留了原始的 requirements / design / tasks。实现与规格的主要差异：

1. 规格写的是「原生小程序 + 微信云开发 CloudBase」，本项目改成「小程序 + H5 双端 + 自建 Node 后端」—— 这样 H5 端可以在浏览器里真实验证全部业务逻辑，验证过的同一套逻辑再给小程序用；同时不绑定云厂商。
2. 绑定码机制是规格空白处补齐的（见上文）。
3. 规格里的 tasks.md 全部未勾选，本次实现覆盖了 M1 身份角色、M2 作业主流程、M3 接娃通知（除订阅消息）、M4 积分排行、M5 商店兑换、M6 错题集、M7 管理强化与审计。
